# 运行监测与批次复盘

## 目的

让每次 Shawn-PPT-image 真实任务在不增加 ImageGen、不打开图片、不阻塞交付的前提下，留下可复盘的技术健康报告，并把不同对话的已完成运行和已明确终止运行登记到同一个项目级索引。后续专门的审查对话、手动任务或定期任务可从全部记录、任意数量的最近记录或尚未复盘记录中选取批次，不扫描旧聊天和原始日志。

监测层是正式状态的只读派生层：

- `style_run_state.json|selected_style_run_state.json` 仍是唯一进度真相。
- `handoff.json` 仍是正式交接。
- 监测失败不能回滚 `process_completed`、不能阻断交付、不能触发重生或修改候选。
- 技术报告不等于审美、内容、空间或工艺质量门。

## 每次运行的自动产物

`process_completed` 封存正式状态和 handoff 后，`pipeline_control.py` 自动、尽力而为地生成：

```text
<project_dir>/state/run_health_report.json
<project_dir>/state/run_health_report.md
```

报告只读取已有状态、任务、哈希、路径和计时，检查：

- 正式候选、总览、handoff、状态与哈希是否一致。
- 图片调用、重复绑定、恢复、技术重试和元数据 fallback。
- A–H 提示指纹、中间产物投影、提示内完全重复长段落。
- 参考图、证据与必需资产的角色、路径、输入清单和最多五个图片输入边界。
- 任务包到派发、图片工具、文件绑定、Agent 尾部、Judge/总览与流程总耗时。
- 调度队列、事件序号、请求到交付的 15 分钟软目标和可观察的空转长尾。

报告不得包含原始提示词全文、图片像素、Base64、缩略图、原始聊天或子 Agent JSONL。`health_status=healthy|attention|defect` 只描述非视觉技术健康。

## 项目级集中索引

新任务的 `state/task_init.json` 记录 `monitoring_root` 与 `monitoring_mode=background_non_blocking`。解析优先级：

1. `init_task_dir.py --monitoring-root` 显式路径。
2. `SHAWN_PPT_MONITORING_ROOT`。
3. 当前目录或父目录的 `.shawn-ppt-image-monitoring.json`。
4. `~/.codex/shawn-ppt-image-monitoring.json`。
5. `<output_root>/_skill_monitoring/shawn-ppt-image`。

集中目录使用：

```text
<monitoring_root>/
  entries/
    entry_<run-id-hash>.json
  reviews/
    review_<entry-id>.json
  index.json
  index.md
```

每个运行只写自己的不可冲突 entry；`index.json|md` 可从 `entries/` 确定性重建。索引记录运行 ID、模式、页码、结果、完成或终止时间、健康状态、问题代码、调用/恢复/计时摘要以及本地报告路径，不复制完整事实或提示。`completed_run` 与 `terminal_incomplete_run` 分开统计；临时 `diagnostic_snapshot` 仍只留在任务目录，不进入中央索引。

`index.json` 同时提供：

- `run_count`：已登记的真实任务记录总数。
- `summary.completed_run_count|terminal_incomplete_run_count`：完成与明确终止任务分开计数。
- `summary`：健康状态、运行模式、问题代码、已完成 Review、待复盘和待处理结论数量统计。
- `pending_reviews`：默认增量审查队列，只包含 `review_status=pending` 的新记录。
- `deferred_resolutions`：已经审查但结论明确延后处理的工作项；它不是重新审图队列。
- `recent_10`：最近十次运行，只用于浏览和定位，不是默认审查队列。
- `runs`：全部轻量记录。
- `review_selection_policy`：机器可读的增量选择、历史重审和回归基线政策。

## 非阻塞规则

- 完成任务的自动监测只在 `process_completed` 正式状态和 handoff 已落盘后运行；中止、替代或阻塞任务须由主控明确写入终止结果和原因，不得把普通 running 快照自动当成终止。
- 本地报告或集中索引写入失败时，只在命令结果返回 `monitoring.status=warning`；正式状态保持 completed。
- 监测不属于 Fast8 的 15 分钟端到端生成软目标，不增加图片调用、Judge、视觉 Worker 或自动修复；集中索引写入不得阻断可点击交付。
- 集中索引不打开总览或单图。后续审美 Review 必须在新的隔离视觉任务中按需读取。
- `validate-state --complete` 不以监测索引为硬门，避免监测存储短暂不可用时影响正常工作。

## 手动恢复与索引重建

自动监测失败或需要为历史完成运行补登记时执行：

```bash
python3 scripts/pipeline_control.py write-run-health \
  --state "<project_dir>/state/style_run_state.json"
```

中断中的任务只做诊断时可显式增加 `--allow-incomplete`；它只写当前任务的本地报告，不进入集中索引。若任务已经真实发生且明确被替代、中止或阻塞，应登记终止结果：

```bash
python3 scripts/pipeline_control.py write-run-health \
  --state "<project_dir>/state/style_run_state.json" \
  --allow-incomplete \
  --terminal-outcome superseded \
  --outcome-reason "<可审计的终止原因>"
```

这会写入 `terminal_incomplete_run`，但不会伪装成完成运行，也不会补造候选、总览或 handoff。

集中索引需要重建时执行：

```bash
python3 scripts/pipeline_control.py rebuild-monitoring-index \
  --monitoring-root "<monitoring_root>"
```

## 后续批次复盘

专门的审查对话或定期任务默认只读取 `index.json.pending_reviews`，再读取这些新增记录对应的 `run_health_report.json`、正式 handoff、内容合同和必要视觉总览。不得用 `recent_10` 直接构造待审批次，也不得默认打开全部单图或读取旧聊天。

`review_status=completed` 表示该运行已经完成一次正式复盘，不会因为后来新增任务、重建索引或修改 Skill 而自动重新进入 `pending_reviews`。Skill 修改后的效果应通过新的真实运行验证；旧运行只能作为只读回归基线，不创建第二份同类 Review，也不重复计入新问题样本。

只有以下情况允许重新读取已完成 Review 的历史运行：

1. 用户明确要求重审某条历史记录；
2. Review 文件无效、与 entry/run/overview 哈希不一致，需要修复原 Review；
3. 新旧回归对照需要旧图作为基线。此时只审新的运行，旧记录保持 completed。

批次复盘应区分：

1. 单次运行操作问题，例如错误命令、环境依赖或偶发路径回传。
2. 可复现管线缺陷，例如反复恢复、路由冲突、重复提示或固定阶段长尾。
3. 审美问题，例如太空、太满、模板化或参考气质稀释；这些不由第一阶段技术报告自动下结论。
4. 用户个人偏好和当前项目适配，不能自动升级为全局规则。

每一条新运行的正式 Review 都必须重新完成一次七问根因检查；即使该轮健康、问题与上一轮相似或准备直接写 `no_change_needed`，也不得沿用旧答案或省略。本轮逐项记录：

1. 为什么本轮会有这个问题，或为什么本轮没有再出现预期问题；
2. 涉及步骤是否必要，若必要，其模型参与和等待方式是否必要；
3. 为什么此前没有发现，或此前发现后仍未真正修复；
4. 之前相同的修改方式是否本身无效、只处理表象或制造新成本；
5. 是否过度纠结签名、哈希、回执、格式等不影响图片结果的细节；
6. 能被本轮证据支持的根本原因是什么；
7. 每一环节是否应换更快模型、降低推理强度、并发执行，或直接由确定性脚本替代。

只要本轮存在失败、重试、恢复、模型返工或因此产生的等待，七问还必须展开两个独立分支，不能把它们合并成“发生过一次失败”：

- `failure_root_cause`：失败究竟发生在哪一层，是输入/合同错误、模型生成的机械代码错误、工具或后端失败、调度/容量问题、路径与落盘问题，还是过严门槛误杀；为什么会发生，能否在派发前预防或由脚本消除；
- `post_failure_handling`：失败发生后，检测、分类、终止、重试或恢复是否及时且必要；是否等待了迟到回执、模型解释、无关审查或错误恢复；一次真实失败是否被管线放大成数分钟长尾或多次返工。

Review 必须分别量化“失败本身耗时”和“失败后处理耗时”；无法直接测量时明确写估算依据。优化优先级先减少可预防失败，再缩短不可避免失败的处理长尾，不能只把恢复做快而放任同类失败重复发生。

Review sidecar 在 `technical_findings.root_cause_review` 中保存本轮七问的简洁答案和证据路径；有失败时再显式保存 `failure_root_cause` 与 `post_failure_handling`。七问是每轮独立诊断，不要求每轮都修改 Skill；证据不足时写明未知并提出最小验证，不以猜测推动返工。

审查结果写入 `reviews/review_<entry-id>.json`。索引只在 sidecar 的合同版本、entry/run 绑定、overview SHA、技术/视觉/速度字段、当轮七问根因检查和隐私声明均通过校验后标为 `review_status=completed`；文件存在但合同无效时标为 `invalid`，没有报告时保持 `pending`。可选 `resolution.status=applied|no_change_needed|deferred|superseded` 记录结论是否已落实；`deferred` 进入独立处理清单，但不会重新触发图片 Review。任何全局 Skill 修改仍须经过跨页面重复证据、受控 A/B、速度回归和用户确认，不能让单次运行自动改写正式 Skill。
