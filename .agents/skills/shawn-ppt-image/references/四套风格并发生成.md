# 四套完整 / 八套快速风格并发生成

本文中的 `output_root` 是共享输出根目录；`project_dir` 是其下本次运行独立的任务目录。必须先按 `SKILL.md` 的“输出根目录与任务目录”规则运行 `scripts/init_task_dir.py`，然后才能创建状态和图片任务；新目录的 `state/task_init.json` 会要求首轮派发前封存来源。本流程不得把任务文件直接写入 `output_root`。大型源 PPT/PDF 默认保留原路径并在 `references/` 记录清单与哈希，只复制必要 Logo、图片资产和实际使用的少量渲染页；不得为任务隔离重复复制或整套渲染大型 OneDrive 文档。

## 目的

两种 4×3 都用同一组三个真实内容页面探索 A/B/C/D 四套视觉方案，共 12 张；Fast8 与经典 Quick8 都用同一个共同代表页探索 A–H 八套方向，共 8 张。所有字母都只是本次运行的临时创意席位，不对应长期固定风格。

4×3 只使用两种模式。默认 Fast 4×3 采用“成品级候选锚点 + 按席位渐进扩展”；严格 4×3 保留“正式锚点 + 阻塞式质量门 + 八页扩展”。未指定版本的 8×1 默认使用 Fast 8×1 Diversity：主 Agent 直接同波派发 A–H 八个图片 Agent，预留第九槽，并在 A–H 齐备后用确定性 contact sheet 和快速低推理隔离 Judge 做一次终局组合差异检查；旧任务仍可恢复其既有增量检查点。原 `quick_8x1` v5 作为经典兼容管线保留。所有首图都是成品级候选，不是低质量草稿。

参考图处理、约束优先级、生成提示边界和工艺门统一按 `参考图与约束分层.md` 执行。风格探索阶段以实际参考图作为高维视觉证据，文字只提炼用户意图，不把参考图拆成组件配方。

## 运行模式

- **Fast 4×3 候选模式**，内部标识 `fast_4x3_anchored`：四套各生成三个代表页，共 12 张成品级候选。用户说“4×3”“4×3 风格定位”“快速 4×3”时默认使用。
- **严格 4×3 模式**，内部标识 `full_4x3_anchored`：同样生成 12 张，仅在用户明确要求全部自动严格验收、可直接正式交付时使用。
- **Fast 8×1 Diversity**，内部标识 `fast_8x1_diverse`：未指定版本的 8×1 默认使用。A–H 八套只生成共同锚点页；A–D 深色、E–H 浅色，总览固定 2×4。新运行必须使用艺术导演 v1 与视觉活跃度组合 v1：共享页级关系命题、审美意图和显式 `flexible_story`，八席分别获得临时且互异的 `visual_thesis`、`craft_axis`、`visual_activity_mode` 与 `attention_strategy`；至少三席为 `restrained`，`expressive` 最多两席。8 个图片 Worker 与 1 个隔离 Judge 并行。Judge 只做组合差异与严重最低工艺/构图健康过滤，最多授权一轮、全运行至多两张新探索。
- **经典 Quick8 v5**，内部标识 `quick_8x1`：保留原有 4–6 个首感席位、2–4 个完全开放席位、并发 8 和选择前不判重语义。只在用户明确指定或恢复旧任务时使用。
- 新运行不再创建 `quick_4x1`；用户明确只要 4 张时先确认是否偏离标准快速模式。脚本仅保留旧 `quick_4x1` 状态的恢复兼容。

四条管线都使用相同的事实、品牌和成品级首轮生成标准。Fast 4×3 与经典 Quick8 在文件验收后标记 `candidate_ready`；Fast8 必须等当前八张的差异 Judge 收口后再标记，但页面仍只有 `filesystem/filesystem_only`，不伪装成正式视觉验收。严格 4×3 的内部四锚点检查通过后自动继续生成另外八张。4×3 不得新增第三种模式。

## 批量内容预检门

在任何图片任务或图片队列出现前，主 Agent 必须按 `内容规划规则.md` 为本次会生成的页面建立 `content_contract_version=2` 内容契约，并按 `空间节奏与视觉呼吸规范.md` 完成定性负载预检。

- Fast 与严格 4×3 都一次预检全部 3 张代表页。
- 两种 8×1 首轮都只预检共同锚点。经典 Quick8 可按旧三页样张工作流保留两个 `deferred_pages`；新 Fast8 是单页探索，不创建占位页。
- 多页 `content_resolution.status=needs_user_decision` 时，只向用户发起一次集中确认，逐页说明移出辅助内容、拆页或调整本页表达范围的影响；不再让用户选择空间档位。
- 从既有 `required_content` 或大纲“必须出现”转换时，先把全部项目视为拟必显集合。预检区分语义焦点、视觉入口和主导阅读结构；并列双重点或有序多节点不因数量而失败。只要存在不改变内容义务的合理组织路径，就记 `spatial_feasibility=pass`；若只有压缩、概括、减少实例、不完整展开或拆页才能同时保证可读性与统一空间标准，则记 `overloaded` 并进入内容决定。Fast 与严格模式使用同一预检结论，不得因此静默删内容或先生成碰运气。
- 用户确认前允许创建仅含预检信息的 `style_run_state.json`，但不得创建 `style_jobs`、`style_contracts`、`style_page_jobs`，`scheduler.active_actions` 与 `scheduler.ready_queue` 必须为空，也不得调用图片后端。
- 用户确认后先把每页最终 `content_resolution`、`display_required`、`display_supporting`、`spatial_standard_version=1` 与 `spatial_feasibility=pass` 写入状态，再创建锚点任务和队列。
- 预检解决后，把当前批次已解决页面各自写入 `content_contracts/page_<ID>.json`；后续锚点和跟随任务必须从同一内容源机械派生，不得在阶段切换时重新整理事实。
- 首轮派发前按 `阶段交接与源材料漂移.md` 精确封存本模式完整页面范围、全部相关内容合同及会进入正式任务 `imagegen_referenced_paths` 的参考图、共享资产和 `required_page_assets`；不得把合同里未路由到图片工具的文件虚报为已使用资产。后续命令换用快照外合同或外部资产、篡改 referenced paths/manifest/fingerprint，或把其他风格/其他 follower 候选当作内部锚点时，必须在写任务、写队列前阻断。
- 使用 `scripts/pipeline_control.py record-event` 在用户决定收到、预检解决和 `style_jobs` 真正创建的当时写入事件。最终状态必须能证明 `preflight_resolved_at <= style_jobs_created_at <= initial_anchor_dispatch_at`，不得用文件修改时间或事后估算代替。旧运行中的 `first_three_way_dispatch_at` 只用于兼容验收，不得用于新运行。

预检阶段 `scheduler.phase=content_preflight`。需要用户决定时使用 `preflight.status=needs_user_decision`；全部页面解决后使用 `preflight.status=resolved`。顶层状态仍为 `running`，不增加新的顶层状态值。

## 选择三个代表页与共同锚点

从当前大纲选择辨识力最高的三页，并记录真实页码、核心结论、内容负载和选择理由。优先覆盖：

- 低或中等负载的观点、叙事或视觉身份页。
- 高负载的数据、证据、案例或对比页。
- 流程、架构、系统或复杂关系页。

这不是固定题型模板，但三个页面必须能检验同一视觉语言如何适应不同内容负载。

从三页中再选择一个共同 `anchor_page_id`：

- 必须能清楚建立背景、字体气质、色彩、材质、页面外壳和空间节奏。
- 必须通过统一空间标准的可行性检查，即 `spatial_feasibility=pass`。
- 辨识力相近时优先选择低或中等内容负载页，不用过载复杂页锁定拥挤的视觉语言。
- 其余两个页面记录为 `follower_page_ids`。

经典 Quick8 可记录全部三页但只激活 `anchor_page_id`，另外两页写入 `deferred_pages`。新 Fast8 只记录用户本次请求的一页，`follower_page_ids=[]`、`deferred_pages=[]`；选定方向后的扩页另建任务。

## 空白创意席位与明暗分组

- 两种 4×3：A、B 固定为深色背景方向；C、D 固定为浅色背景方向。
- 两种 8×1：A、B、C、D 固定为深色背景方向；E、F、G、H 固定为浅色背景方向。
- 用户明确指定的品牌底色、明暗范围或合规要求优先；发生冲突时按用户要求记录实际 `tone`。
- 除明暗与用户硬约束外，不为任何席位预设媒介、流派、字体气质、空间结构、版式家族或长期名称。
- 每次运行重新创造当前模式的四套或八套方案，不继承长期风格映射。新 Fast8 v7 与新 4×3 v6 都写 `art_direction_contract_version=1`：每席有唯一 `direction_id`、互异的 `visual_thesis` 与 `craft_axis`，最终提示指纹也必须互异。经典 Quick8 v5 继续使用 4–6 个首感引导席位与 2–4 个自由席位；已创建的旧 Fast8 v7 与旧 4×3 v6 分别按原 `creative_impulse` 或首感/开放席位合同恢复。
- A–D 没有固定视觉模板，也不对应双栏、环形、蓝图、年报、电影感等预设形式；不得为了填满席位而预分配版式、媒介或视觉流派。
- 不建立双栏、环形、蓝图、年报、电影感或其他视觉形式黑名单；内容适合时图片模型仍可自由采用。页级关系综合不得指定视觉答案；候选级 `visual_thesis` 与 `craft_axis` 可以明确视觉解释与工艺语言，但不得预分配固定拓扑、组件数量或像素方位，也不得虚构事实。
- 第一轮全部锚点独立探索；锚点 Agent 不读取其他席位输出。
- 参考图必须按可选 `style_slots` 或 `tones` 确定性路由。只供浅色席位的参考图不得同时传给深色席位，再靠文字要求模型忽略。
- 每张参考图只记录简洁 `reference_intent.borrow` 与 `reference_intent.do_not_copy`。不得把图中的圆形节点、卡片、线型、分栏或具体构图自动升级为硬约束。

```bash
python3 scripts/init_task_dir.py --output-root "<output_root>" --task-name "<task_name>"
```

两种 8×1 使用同样的公共分类：`references/` 放本任务复制后的参考图与证据，`state/` 放运行状态、布局合同和索引，`style_jobs/results/` 放波次回传、恢复结果和其他中间 JSON，`visual_qa_jobs/`、`visual_qa_jobs/inputs/` 及其 `results/` 分别放隔离视觉审查任务、哈希绑定的确定性 contact sheet 和精简 JSON；Fast8 的 `fast8_diversity_*.json`、审图输入与 Judge 报告只能放在这三级目录，不把临时返回文件放在 `project_dir` 顶层。

新运行还必须在首轮派发前按 `阶段交接与源材料漂移.md` 封存 `state/source_snapshot.json`。恢复、非恢复型派发、Fast 锚点定向修复、Fast/Strict 跟随页创建和正式交接前由 `pipeline_control.py` 复核；`settle-wave` 与 `recover_artifact` 不被该门禁改写。候选与正式总览齐备后生成 `state/handoff.json|md`，再进入用户选择或下游交接。

## 锚点任务

预检解决并写入共同内容合同后，所有探索模式都由主 Agent 先写 `state/layout_portfolio.json`。新 4×3 合同为 v6；经典 Quick8 合同为 v5；Fast8 合同为 v7。新 Fast8 与新 4×3 在现有布局合同上写 `art_direction_contract_version=1`；新 Fast8 另写 `visual_activity_portfolio_version=1`。页面合同同时提供 `visual_quality_intent` 与 `relationship_thesis`，新 Fast8 还提供显式 `flexible_story`。共享语义护栏保留在内容合同与 QA，不在方向组合和 ImageGen 提示中重复维护；不再要求母结构、固定阅读路径、固定 A–H 模板或预设备用返修方向。

Fast8 v7 示例；实际必须完整包含 A–H：

```json
{
  "layout_portfolio_contract_version": 7,
  "art_direction_contract_version": 1,
  "visual_activity_portfolio_version": 1,
  "page_id": "02",
  "director_rationale": "用八个可见关系命题与独立工艺轴扩大真实选择面，不固定具体版式。",
  "styles": {
    "A": {
      "direction_id": "run_local_A",
      "visual_thesis": "让两项能力作为同一系统中的两个连接面，共同收束到一个上位价值",
      "craft_axis": "采用精密工程剖视、真实材料与克制光影，突出结构完整性",
      "visual_activity_mode": "restrained",
      "attention_strategy": "由整体连接关系承担第一眼，其余事实只以低对比证据出现"
    },
    "B": {
      "direction_id": "run_local_B",
      "visual_thesis": "让两股作用力在一个稳定结果上汇聚，形成清楚的因果张力",
      "craft_axis": "采用编辑字体、大胆尺度关系与受控负空间，保持图像主导",
      "visual_activity_mode": "balanced",
      "attention_strategy": "汇聚动作是唯一第一层入口，说明性证据安静并留出停顿"
    }
  }
}
```

`visual_thesis` 与 `craft_axis` 必须按当前页面、本次运行重新创作；前者把页级关系变成候选级可见命题，后者独立打开图像、字体、材质、光感或图文工艺。`visual_activity_mode` 与 `attention_strategy` 控制同一时刻的视觉并发和主从关系。它们都不是事实、布局或 QA 合同。脚本会在写任何 style job 前拒绝空值和各自的规范化重复，并在八份提示编译完、写盘前拒绝重复 `imagegen_prompt_fingerprint`。不做脆弱的跨语言同义句相似度硬门；实际同构交给隔离 Judge 看图判断。新运行首次创建 `style_jobs` 时缺少 `art_direction_contract_version=1`、`visual_activity_portfolio_version=1` 或不满足至少三席 `restrained`、最多两席 `expressive` 会被拒绝；只有已经落盘旧任务继续按原预编译提示恢复。

新艺术导演提示还包含一条通用的叙事收束短句：每席由一个主导视觉动作或关系承担第一层故事，其他必要内容作为从属证据；不得把合同条目机械还原成“标题、主数字、流程带、注释带”的完整解释套件。它不要求单一物体或视觉隐喻，也不禁止内容真实需要的流程、组织树、表格或多节点；这些结构仍须由一个主导关系统领。新 Fast8 还要求内容合同写一句显式 `flexible_story`，不把 `display_flexible` 和语义护栏重复堆进提示；每席的 `attention_strategy` 说明什么负责第一眼、什么退到安静证据层。`visual_activity_mode` 只控制视觉活跃度，不改变内容密度：至少三席 `restrained`，`expressive` 最多两席。

实际测试若出现多席共同收敛到“左右分栏 + 右侧等重清单”或“科技光束 + 同向箭头”，不得把某个构图设成全局禁令。图片提示改用通用图文整合原则：逐字锚点与 `flexible_story` 共同服务于本席的主导关系，不能把内容合同字段边界直接当成版面分区或组件边界；左右分区、条目、卡片、流程和箭头在内容确实需要时仍可使用，但必须由清楚关系和阅读入口统领。这样约束的是“默认模板化翻译”，不是合法视觉形式。

```json
{
  "layout_portfolio_contract_version": 6,
  "page_id": "02",
```

## Fast 8×1：并行差异裁判与一轮替代

`prepare-anchors` 为 Fast8 写入 9 个子 Agent 槽位，但只有 8 个图片槽；第九槽留给一个 `fork_turns="none"` 隔离 Judge或无生图恢复。新 Fast8 默认等 A–H 齐备后只运行一次终局 Judge：

```bash
python3 scripts/pipeline_control.py prepare-fast8-diversity-review \
  --project-dir "<project_dir>" \
  --state "<project_dir>/state/style_run_state.json" \
  --checkpoint 8
```

`--checkpoint 4|6` 仅保留给旧任务恢复或人工诊断，不是新运行的默认调度。终局命令在 `visual_qa_jobs/inputs/` 生成低负载 contact sheet，并把绝对路径、SHA-256、尺寸、席位、完整候选集合哈希、正式报告输出路径与预编译 JSON 骨架写入 job。job 只交给不把像素内容写入 Codex 会话的对话外 Judge；该运行时先运行 `check-fast8-judge-job` 取得机器绑定的 job SHA、contact sheet、报告路径和骨架，再且只查看 contact sheet 一次。若绑定 `global_chrome_contract`，同一 Judge 同时执行大纲标题区的近似硬合同检查。主控只轮询报告文件；运行时不可用时记录“未执行视觉检查”，不得启动 Codex Judge 或让任何对话打开候选、contact sheet、单图或总览。`final_initial` 绑定当前完整 A–H，只返回 `pass|replace`；唯一一轮替代后的 `delta_recheck|final_recheck_fallback` 只返回 `pass|best_effort`。报告 `summary` 不超过 300 字符。

Judge 报告保存到 `visual_qa_jobs/results/`，然后原子应用：

```bash
python3 scripts/pipeline_control.py apply-fast8-diversity-report \
  --project-dir "<project_dir>" \
  --state "<project_dir>/state/style_run_state.json" \
  --review-job "<绝对路径>/fast8_diversity_8_<hash>.json" \
  --report-file "<绝对路径>/visual_qa_jobs/results/<report>.json"
```

新任务使用 Judge v2 与 `scope=diversity_and_minimum_craft`；旧 v1 / `diversity_only` 任务按原合同恢复。脚本校验 report 与正式 job SHA、候选集合 SHA、当前图片哈希和对应版本的字段边界。v2 除碰撞组外最多记录两项严重 `craft_red_flags`；单席必须同时命中 2–4 个允许的问题类型。除默认组件、粗糙容器、图标和微观工艺问题外，允许报告 `competing_first_level_zones`、`explanatory_module_overload`、`decorative_node_overload` 与 `edge_pressure_without_pause`。轻度卡片感、普通高密度、与参考图不够像或主观“不够漂亮”不能形成替代证据。`replace` 只在 `high_confidence=true` 时有效，并必须给由碰撞组或严重红旗覆盖的 1–2 席各写一句开放、正向、最多 160 字的 `replacement_brief`。两类原因共用同一替代预算。脚本把替代任务写入 `style_jobs/repair_jobs/*_fast8.json`，但旧图只保存在 `repair_source`、报告绑定和 `attempt_history`，不进入 `imagegen_referenced_paths`，避免图片模型继续复刻旧构图。

替代通过原有 `record-dispatch-wave` 和 `settle-wave` 派发、结算、恢复与审计；队列项仍标记 `diversity_replacement=true` 以保持状态兼容。替代成功后状态变为 `recheck_required`。新的最终任务优先使用 `delta_recheck`，只把已变化席位以及原报告中与之相关的 `collision_groups|craft_red_flags` 证据范围交给 Judge，同时用 `full_candidate_count=8` 和完整 A–H 集合 SHA 绑定最终决定；如果历史报告没有足够证据边界，才使用一次 `final_recheck_fallback` 全量复核。两类替代后复核都只允许 `pass|best_effort`，不得授权第二轮替代。全运行最多两张、每席最多一次、最多一轮；若复核后仍有局部问题，Judge 返回 `best_effort` 并以备注结束，不得继续生图。最终 `pass|best_effort` 的 `candidate_set_sha256` 必须与交付时八张一致，否则脚本拒绝 `candidate_ready`、正式总览和流程完成。

## 严格 4×3：四锚点检查与风格合同

四个锚点都有可读、比例有效且已绑定工具事件的 `selected_source` 后，主 Agent 立即生成：

```text
overview/ABCD_anchor_checkpoint.png
```

该文件是严格 4×3 的内部检查点，不是 Fast 模式交付，不暂停等待用户选择。根任务不得打开它；由隔离视觉 Reviewer 子 Agent 按 `prompts/visual-review-worker.md` 的 `qa_anchor_overview` 合同检查，只回传精简 JSON、路径与哈希：

1. `content_gate`：逐字检查 `display_required`，按语义检查 `display_flexible`，并用完整事实库与语义约束核对准确性。
2. `spatial_gate`：按统一空间标准检查整齐而不机械的秩序、隐形网格和精确对齐、组内紧组间松、有限规则的重复、形成层级与阅读路径的对比，以及承担聚焦、分组、停顿和边缘缓冲的有效负空间。信息密度高本身不失败；并列双重点本身不失败，图文重复只作为冗余负载诊断。
3. `craft_gate`：是否命中参考意图、具有清楚视觉签名与精细完成度，是否明显退化为默认企业模板或组件拼装。
4. 单图基础质量：必要素材、Logo、16:9、截断、重叠、水印和结构完整性。
5. 第一眼能否找到观点与阅读入口，视觉是否真正解释、强化或组织信息。不得仅因插画感、海报感或大幅视觉判失败；只有视觉与内容脱节、遮蔽必显信息或造成误导时失败。
6. A/B/C/D 是否像四个不同创意团队；只换底色、强调色或图片不算不同。

## Fast 4×3：锚点渐进解锁

- `content_gate.status=pass|fail|needs_content_decision`，并记录缺失、错误或误导项。
- `spatial_gate.status=pass|fail|not_applicable`，并记录统一空间标准的客观失败项；只有 legacy 运行才沿用原空间档位记录。
- `craft_gate.status=pass|fail|not_applicable`，并记录模板化、参考意图命中、工艺一致性、视觉签名或跨风格差异等可观察结果。

不得用一个模糊的 `qa_note` 同时代表事实完整和统一空间标准通过；`qa_note` 只保留简短总括。

动作边界默认调用 `pipeline_control.py record-event`，由脚本同时写入规范字段和 append-only `events`。新运行由 `prepare-anchors` 写入 `state_audit_contract_version=2`；已经存在 `style_jobs_created` 的旧任务保持 legacy v1，不静默升级。Strict/Fast 4×3、Fast8 与经典 Quick8 的实际图片派发都使用 `record-dispatch-wave`，结果使用 `settle-wave`。Fast8 的差异 job/report 由两个专用命令原子写入，不能让 Judge 直接修改公共状态。批量结算必须优先保留真实且彼此独立的 Agent/图片工具起止时间、`tool_call_id`、`savedPath`、文件大小和 SHA-256。所有 ISO 时间接受显式 UTC 偏移，也接受标准 `Z|z` 结尾并在解析时等价为 `+00:00`，调用方不再人工改写真实时间字符串。Fast8 若已得到可读的绝对 `savedPath`，控制器立即把它作为 `direct_tool_result` 绑定；缺失的 `tool_call_id` 可从标准 `exec-<UUID>.png` 文件名确定性提取，缺失的时间可由正式派发边界、文件 mtime 与结算时间补齐并写入 `timing_capture=controller_bounded_fallback`。恢复已经找到原 PNG、但同 Worker 回传仍缺原图片工具元数据时，`settle-wave` 还会优先复用恢复队列中保存的原值；若原值本身为空，则用原生成派发边界、原图 mtime 和恢复开始边界做受控夹取，写入 `timing_capture=controller_bounded_recovery_fallback`。不得因此手工猜时间、重复 settle 或重生图片。这类 Fast8 元数据补齐不得误报为 `artifact_handoff_unresolved`。Quick8 与两种 4×3 继续使用原有 v2 完整真实元数据要求。

成功生成必须记录真实 `tool_call_id` 与 `selected_source`。如果图片工具事件明确完成且 `savedPath` 可读，立即登记并释放活动槽位；不得等待 Agent 的迟到文字报告。若工具事件尚未完成，不得仅凭目录最新文件猜测路径。

恢复旧运行时，若页面任务没有 `content_contract_version=2`，或使用旧 Fast v4/旧 Strict 无 v6 布局合同、旧 v3 图片提示，就按原 `required_content`、原布局/提示版本、旧状态字段和旧 QA 记录继续恢复，不迁移或重编历史文件。`quick_8x1` v5 不得在恢复时改成 Fast8；`fast_8x1_diverse` 也不得降级为 v5。

## 并发派发

### 严格 4×3 四锚点阶段

- 使用 `prompts/style-worker.md`。
- A/B/C/D 四个席位各有一个独立锚点 Agent，使用 `fork_turns="none"`。
- 初始必须在同一派发波次请求 A/B/C/D 四个席位，不得人为把 D 留在队列等待。
- Worker 只读取 `record-dispatch-wave` 成功返回的 `tasks[]` 同项 `generation_job_path`，读取前核对同项 `generation_job_sha256`；核对通过后才逐字使用正式任务预编译的 v4 `imagegen_prompt` 与 `imagegen_referenced_paths`，不得在派发后重新组织提示。
- 锚点 Agent 只调用一次图片后端；工具完成后该 Agent 不执行 QA。
- 锚点 Agent 在工具结束后立即返回最小文件绑定 JSON，必须包含实际 `tool_call_id`、`savedPath` 和工具起止时间；缺少路径时返回 `artifact_handoff_unresolved`，不得自行再次生图。
- 获取可读 `savedPath` 后立即补派队首动作，不等待文字总结。
- 若运行时返回 `agent thread limit reached`，未获槽位的席位保持在 FIFO 队首；这只是正常背压，不计尝试、不标失败，任一槽位释放后立即补派。

### Fast 4×3 阶段

- 主 Agent 在一个派发动作中直接请求 A–D 四个 `fork_turns="none"` 锚点 Worker；有效并发取运行时可用槽位与待派数的较小值。Worker 只读取 `record-dispatch-wave` 返回的正式 `generation_job_path`，核对对应 `generation_job_sha256` 后才逐字使用任务预编译的 v4 提示。
- 新 v6 运行把 `active_child_limit` 固定为 9，且主 Agent 不计入这 9 个槽位；第九槽位可供滚动派发、无生图恢复或可选隔离 QA 使用，不要求虚构第九个 follower 任务。
- Fast 使用滚动并发：哪个锚点先完成文件校验，哪个席位就先运行 `prepare-fast-followers --styles`，读取其 `dispatch_ready` 并把两张预编译 follower 任务加入当前可派集合；不得等待全部锚点或全部风格合同。
- 锚点与 follower 可以同波在途；始终按 `active_child_limit` 补满空闲槽位。同一风格的两张 follower 可以并发，不需要串行等待。
- 锚点与跟随页首轮都只调用一次图片后端。统一空间标准已进入提示，但选择前的非硬伤空间问题、轻度模板感和审美偏好不得创建 `repair_anchor|repair_page`。
- 明确内容硬伤或锚点实质同构最多允许一次定向锚点修复；跟随页选择前不做视觉修复。
- 12 张有效图片齐备后立即生成 4×3 总览并标为 `candidate_ready`，不等待阻塞式最终视觉 QA。

### 两种 8×1 八锚点阶段

- Fast8 v7 与经典 quick8 v5 都使用 `prompts/style-worker.md`；`style-wave-dispatcher.md` 仅供旧 v3 项目恢复。新 Fast8 预留第九槽，默认在八张已经齐全时创建一个使用 `prompts/diversity-judge-worker.md` 的终局无历史 Judge；旧任务仍可按原 4/6 检查点恢复。
- 主 Agent 在一个派发动作中直接创建 A–H 八个 `fork_turns="none"` 图片 Worker，不经过 dark/light 中间调度。两种模式的有效图片并发都为 `min(8, 当前运行时可用子 Agent 槽位, 8)`；Fast8 第九槽只给 Judge，不能派第九个图片任务。
- 每个图片 Agent 只读取自己的任务和 Worker 协议；彼此不读图片、不做 QA、不写公共状态。新 Fast8 Worker 在同一次 ImageGen 的 `functions.exec` 中写入 job 指定的唯一最小 `worker_receipt`，让状态机不依赖最终文字回合交接路径。
- 新 Fast8 的 `record-dispatch-wave` 为每席返回 `worker_ticket_path`；Worker 先运行 `check-fast8-worker-ticket`，从机器结果取得 job 路径、SHA、图片指纹与回执路径，不在自然语言中转抄 64 位 SHA。经典 Quick8 仍按正式 `generation_job_path|generation_job_sha256` 校验。校验通过后的第一项外部动作即图片工具，不在生图前 commentary、重写提示或读取额外资料。
- 创建新 Fast8 Worker 后，主控立即用 `bind-fast8-worker-sessions` 把真实 `agentThreadId` 绑定到席位。哪些席位先返回，主 Agent 就先结算哪些席位；最终 JSON 缺路径时 `settle-wave` 先合并有效 `worker_receipt`，回执仍无路径则直接检查该绑定 session 下是否恰有一个 `exec-*.png`。只有 session 目录不存在或产物不唯一才进入无生图恢复。不得等全部 Agent 的文字回合结束才登记已经完成的图片工具结果。
- 经典 Quick8 八张齐备后直接生成 2×4 总览。Fast8 八张齐备后先应用绑定完整 A–H 的最终差异报告；若替代，最多两张可并行并在释放的图片槽位中派发，结算后优先做变化席位与原碰撞组的 delta 复核，只有缺少安全边界时才全量复核一次。只有 `pass|best_effort` 才生成正式总览。两者根任务都不得打开图片。

## 悬挂回收与防重复

状态文件和已完成工具事件是恢复依据，不从聊天记忆猜测。

- 工具事件完成且绝对 `savedPath` 可读时，生成阶段已经完成。Fast8 控制器应立即按 `direct_tool_result` 绑定；缺失的标准调用 ID或时间元数据按上文确定性补齐并标记 fallback。其他管线仍要求原有完整元数据。Agent 的文字回传、总结或回合关闭悬挂不得阻塞登记、补派和里程碑计算。
- 回收路径必须来自对应工具事件并与真实或从标准文件名确定性恢复的 `tool_call_id` 绑定；不得选择目录中“最新文件”。
- 只有工具事件完成、未返回明确错误且 `savedPath` 真正缺失、不是绝对路径或不可读时，才分类为 `artifact_handoff_unresolved`。页面保持当前生成动作，先派发同一 Agent 的 `recover_artifact` 回合；该回合禁止调用图片后端，只检查上一工具结果和本 Agent 的准确生成目录并返回绑定 JSON。Fast8 仅缺 `tool_call_id` 或计时字段而已有可读绝对路径时不进入恢复；其他模式继续按原结算合同校验字段完整性。
- 同一 Agent 仍无法恢复时，主 Agent 运行 `scripts/recover_image_artifact.py`。脚本只接受工具调用准确时间窗内唯一、有效且尚未被状态绑定的 PNG；从唯一文件名恢复 `tool_call_id`，校验尺寸、大小和 SHA-256 后登记。脚本返回多个候选时必须等待同波其他结果绑定并再运行一次，不得选择最新文件。
- Fast8 新任务在最终 JSON 缺路径时先读取同次调用 `worker_receipt`。若回执缺失，只要已有原工具准确时间窗或准确会话目录，就可立即并行启动原 Worker 的只读恢复与确定性脚本，无需等待固定 45 秒。两者都是只读恢复，先得到唯一合法绑定的一方用于一次结算；迟到结果不得重复写状态。脚本若为 `ambiguous|not_found`，继续等待另一条路径，不改变原有“两份独立 not_found 才能授权技术重试”的门槛。
- 主 Agent 不得为找路径而打开、整段读取或复制子任务原始 `.jsonl`。同一 Worker 只回传最小绑定 JSON；脚本恢复同样只把精简结果写入 `style_jobs/results/`。根任务不接收完整工具日志、图片块、Base64 或历史对话。
- 恢复成功的结算结果必须使用 `action="recover_artifact"`，并包含原始 `source_action`、原始图片工具时间、`recovery_started_at`、`recovery_finished_at` 与 `recovery_method=same_worker|deterministic_script`；不得伪装成新的 `generate_anchor`。`settle-wave` 会成对记录 `artifact_recovery_started|finished`，且不会增加图片 `attempt_count`。
- 产物恢复不增加 `attempt_count`，也不占用图片尝试预算。只有新的图片后端调用才算一次尝试。
- 发起重试前必须检查当前尝试是否已有完成工具事件、可读文件、唯一未绑定候选或已登记哈希。任一存在都禁止重复生成。缺文件时的两份 `not_found` 证据必须来自同一 `source_action + attempt` 的两个独立阶段：先由 `same_worker` 恢复，再由 `deterministic_script` 在准确时间窗内恢复；重复同一种方法不构成第二份证据。两者均为 `not_found` 后，`artifact_recovery_finished` 会原子关闭 active recovery、归档失败来源并把原生成动作的 `attempt+1` 排入 `ready_queue`；恢复方法、尝试或时间不匹配会直接拒绝。
- Agent 动作长尾与图片工具长尾分别统计。超过 Agent 软告警线时可中断已无待处理工具的回合；不得把 Agent 长回合错误归因给图片后端。
- 图片工具仍运行时继续监控；只有工具明确失败、取消或无可恢复结果时才进入重试预算。
- 每次用户可见进度都来自状态文件，说明已完成、在途和下一动作。

确定性恢复示例：

```powershell
$env:PYTHONUTF8 = "1"
$python = (Get-Command python -ErrorAction Stop).Source

& $python $recover `
```

## 隔离视觉质检

根任务不得调用图片查看工具、打开总览/原图或在回复中嵌入图片。视觉审查必须派发给隔离子 Agent 中的 Reviewer/Judge；它们可按任务需要打开 contact sheet 和必要单图，但只向根任务回传精简 JSON、路径、尺寸、哈希和状态，不回传图片块、截图、缩略图、Base64 或 Data URL。`prompts/visual-review-worker.md`、`prompts/diversity-judge-worker.md` 和 `prompts/global-chrome-review-worker.md` 是这些隔离 Reviewer/Judge 的文字合同。审图通道不可用时必须暂停需要视觉结论的步骤，不得伪造通过。用户交付只给普通可点击文件链接。

### 锚点检查

严格 4×3 由 `qa_anchor_overview` Worker 检查四张锚点的单图客观质量、参考意图命中、工艺完成度与跨风格差异，并分别报告 `content_gate`、`spatial_gate` 与 `craft_gate`；只有三个质量门都通过后才创建合同和后续任务。

Fast 4×3 不做三道正式质量门。默认完成确定性文件检查后就渐进扩展，不增加阻塞式视觉 QA。若项目确实需要可选的 `qa_fast_anchor_checkpoint`，它只报告硬伤和实质同构，并限制在短回传；必须在受检席位创建跟随合同之前完成。只有报告确认可观察硬伤或实质同构时，才能按“Fast 4×3：锚点渐进解锁”的命令调用一次 `prepare-fast-anchor-repairs`，且必须先结算修复再扩展该席位。统一空间标准必须进入提示，但选择前不能单独授权空间返修；未启用该检查时，锚点的其他视觉问题留到用户选择后只收口所选风格。

经典 quick8 v5 不创建分组 QA Agent，也不做选择前三道质量门。新 Fast8 的 `diversity_and_minimum_craft` Judge 不执行完整文字、统一空间或工艺三门；最低工艺过滤只识别同时具有至少两类严重客观退化的席位，不给页面写任何三门 `pass`。若该运行绑定并适用 `global_chrome_contract`，同一个最终 Judge 只追加大纲明确要求的标题区近似检查，不评价正文审美，也不增加第二次接触表查看。没有大纲标题要求时不增加该字段。既有 Fast8 v1 继续使用 `diversity_only`。两种 8×1 的根任务都只通过文件元数据确认八张路径可读、尺寸有效、比例为 16:9 且没有空文件；不得查看 2×4 总览。旧 v4 同样不创建分组 QA；旧 v3 项目仍可按原 `prepare-quick-qa` 恢复。

### 9/12 里程碑

首次达到 9 个可读且比例有效的 `selected_source` 时，立即用 `--allow-invalid` 生成一次带占位符的 4×3 里程碑。需要提前检查时只派发隔离视觉 Reviewer；根任务不得打开里程碑，也不得中断仍在运行的图片工具或等待修复后再派尚未生成的正常页面。

### 严格 4×3 最终总览

12 个单元格都有可读原图后生成最终临时总览，由 `qa_final_overview` Worker 检查：

1. 内容门：只按 `display_required` 检查画面必须直接可见的信息是否准确、完整、无误导；同时用 `source_facts`、语义约束和来源核对事实，不要求它们逐条出现在画面。
2. 空间门：按统一空间标准检查。页面应整齐但不机械，具有一致的隐形网格、对齐轴、基线、边界与间距节奏；相关内容组内紧、组间松；少量规则重复一致，对比形成层级和阅读路径；有效负空间承担聚焦、分组、停顿和边缘缓冲。信息密度高本身不失败，但近似对齐、挤边、缩字或等重卡片墙应失败。重复表达只作为可能增加冗余负载的诊断项。
3. 工艺门：是否命中参考意图和锚点工艺、具有清楚视觉签名与精细完成度，是否出现默认模板、通用组件拼装、图标线条不统一或明显工艺退化。
4. 单图基础质量：必要素材、Logo、16:9、截断、重叠、水印和结构完整性。
5. 组内：同一风格三页是否继承锚点的色彩、字体气质、材质、图像工艺和页面外壳，同时构图是否随内容变化。
6. 跨风格：四套是否像不同创意团队，只换颜色或图片不算真正不同。
7. 内容属性：第一眼仍是用于讲清观点的 PPT；视觉可以强烈，但必须与内容协同，不存在已经造成冗余负载的无效完整重复。

### Fast 4×3 最终总览

12 个单元格都有可读、比例有效的原图后立即生成正式 4×3，总览与单图状态写为 `candidate_ready`。选择前不创建阻塞式 `qa_final_overview`；用户明确要求自动检查时，由隔离视觉 Reviewer 生成报告，只作候选备注，不自动返修。用户选定风格后，才对该风格三页执行严格内容、空间和工艺门。

只有隔离视觉 Reviewer/Judge 报告中的 `suspect_paths` 才能按 `qa_suspect_pages` 合同单独打开。根任务始终不打开原图。修复后只复查新图及受影响的组内关系，不重复读取全部合格原图。

### Fast8 大纲标题区近似遵循 QA

只有大纲或用户当前要求明确规定标题区并绑定 `global_chrome_contract` 时，最终差异 Judge job 才加入短标题区检查，并在同一次 contact sheet 查看中完成。详细协议见 `全稿外壳与标题系统.md`。它只检查来源明确要求的 Logo、标题层级和大致位置；不测像素、不要求参考图坐标一致。固定标题区的存在不构成空间失败，正文审美与差异也不在该子报告范围。

`apply-fast8-diversity-report` 同时校验并写入 `global_chrome_review`。只有明显违背大纲才为失败；存在 `unknown` 时再按需补单图诊断，不得猜测。轻微坐标、字号、间距和生成误差不构成失败。正常 Fast8 不再派发第二个独立标题 Reviewer；`prepare-global-chrome-review` 只保留为异常诊断和旧任务兼容入口。

### Fast8 可选后置效果复盘

用户或实验任务要求在正式 Fast8 完成后评价网页创意导演感时，由一个隔离视觉 Reviewer 执行 `qa_fast8_effect_overview`。它不是差异 Judge，也不是正式内容、空间或工艺门：只查看最终 2×4 总览一次，评价关系命题的第一眼可见性、A–H 真实分离、卡片/逐行罗列风险、空间层级、完成度、最强/最弱席和残余创意差距，并明确总览尺度无法核验小字、Logo 与逐项事实。报告不得改写已封存状态，耗时单独记录且不计入正式 Fast8；隔离审图通道不可用时记录未执行，不伪造结论。

## 重试规则

主 Agent 在写入修复队列前，先用确定性路由工具核对质量门组合：

```powershell
& $python $control route-failure --content-status fail --spatial-status pass
& $python $control route-failure --content-status pass --spatial-status fail
& $python $control route-failure --content-status pass --spatial-status pass --craft-status fail
& $python $control route-failure --content-status needs_content_decision --spatial-status pass --content-structure-overloaded
```

输出只允许 `content_repair`、`visual_repair`、`content_decision` 或 `accept`。路由工具不代替主 Agent 判断质量门，但一旦质量门状态确定，就不得绕过路由结果重复抽样。

以下构图撞车返修命令只用于恢复旧 Quick8 v3，不用于经典 Quick8 v5、Fast8 v7 或任一 4×3 v6：

```powershell
$collision = '{"C":"与 B 共享左右双栏和中央连接器","D":"与 A 共享左塔、中 Logo、右列表"}'
& $python $control prepare-diversity-repairs `
  --project-dir "C:\绝对路径\项目目录" `
  --styles "C,D" `
  --attempt 2 `
  --collision-details-json $collision
if ($LASTEXITCODE -ne 0) { throw "差异返修任务创建失败" }
```

同一批旧 v3 失败席位必须一次传入，或依赖 `diversity_repair_allocations.json` 延续已有分配。非旧 Quick8 v3 调用该命令会明确拒绝；Fast8 只使用 `apply-fast8-diversity-report`，Fast 4×3 只使用问题导向的 `prepare-fast-anchor-repairs`，Strict v6 继续按正式 QA 路由定向修复。

- 图片生成 Worker 不执行视觉质量自主重试。严格 4×3 的质量重试由主 Agent 根据隔离视觉 QA 报告授权；Fast 4×3 与经典 quick8 v5 选择前不授权审美或非硬伤空间视觉重试；Fast8 只接受正式差异报告授权的一轮组合替代。
- `display_required` 缺失、错误或产生误导时，记录 `content_gate=fail` 并做内容修复。
- 严格模式中，内容契约可行但构图拥挤、入口争抢、负空间失效、边缘封闭、Takeaway 过强或无效重复已破坏空间层级时，记录 `spatial_gate=fail` 并做定向视觉修复。Fast 4×3 中这些只作候选备注，除非已经造成不可读、裁切或结构崩坏等硬伤。
- 严格模式中，页面明显模板化、参考意图未命中、工艺不统一、视觉签名不足或跟随页相对锚点发生明显工艺退化时，记录 `craft_gate=fail` 并做定向视觉修复；锚点合同锁定前最多允许一次。Fast 选择前只有明确硬伤或锚点实质同构可触发一次 `prepare-fast-anchor-repairs`，轻度模板感与主观偏好只作候选备注。不得以“想看另一版”替代客观症状。
- 首张图空间失败不等于内容过载。先判断是否存在不改变内容义务的视觉修复路径；若存在，走 `visual_repair`。如果只有移出、压缩、改写或拆分内容才能解决，立即记录 `content_gate=needs_content_decision`，停止该页的同提示抽样并重新触发内容过载确认；不得机械耗尽视觉重试次数后才询问用户。
- `content_resolution.moved_items` 中已获用户许可移出的内容不构成遗漏；只有用户确认后仍列在 `display_required` 的项目才触发内容失败。
- 单页客观失败只重试该页；合同锁定后的修复使用新的无历史 Agent，继续读取同一风格合同和锚点。
- 单页与另一套趋同只重试该页；此规则适用于严格 4×3 和旧 quick8 v3。Fast 4×3 只在锚点实质同构时允许一次定向修复；经典 quick8 v5 的相似候选照常进入总览；Fast8 只替代 Judge 选出的最冗余 1–2 席，其他候选不动。
- 严格 4×3 整套三页与另一套实质重复时，重做该套必要页面；只提供必须避让的结果，不预设替代媒介或流派。
- 已验收的其他页面和风格不得重做。
- 多个失败项进入同一 FIFO 修复队列，按当前模式并发上限和运行时可用槽位回退；Fast8 图片动作在途仍不得超过 8，第九槽保留给 Judge。
- 严格 4×3 每页最多 3 次总尝试。Fast 4×3、Fast8 与经典 quick8 v5 的正常页面选择前只有 1 次首轮图片调用；`recover_artifact` 与孤立文件恢复不计尝试。Fast8 每席最多 1 次差异替代，全运行最多 2 席；任一失败图片动作确认无产物后才允许 1 次技术重试，不能把总 attempt 上限解释为自由重抽预算。
- `Bad Request`、请求无效或同等技术错误且无 `savedPath` 时，先做无生图产物恢复，以排除错误响应但文件已经落盘。确认 `not_found` 后，第一次只允许同一 Agent 做一次“事实不减、请求精简”的技术重试；连续第二次相同错误时立即阻塞，不使用第三次通用尝试预算。仅有 `missing_saved_path` 或 `artifact_handoff_unresolved` 不足以授权重试。
- 单纯主观偏好或想多抽一次不触发重试。严格 4×3 与 Fast 4×3 仍按各自门限处理“明显默认模板、没有参考意图要求的视觉特征、与另一席位实质同构、工艺显著低于锚点”等可观察失败；经典 Quick8 v5 选择前不因此返修。新 Fast8 只有最终正式组合报告确认的高置信度实质同构，或单席同时命中至少两类严重最低工艺红旗时，才能触发同一轮、至多两席替代；轻度模板感、共同配色、主观审美、参考不够像或小文字问题均不授权替代。旧 Fast8 v1 仍只按实质同构替代。

## 自动收口

- 严格 4×3 四锚点通过后立即创建合同、八个后续任务及其预编译 v4 提示，不等待用户消息。
- Fast 4×3 每个锚点完成文件校验后立即渐进创建本席位合同与两张预编译 follower 任务，并用 `--tasks-json` 在剩余锚点旁滚动补派；12 张齐备且派发审计覆盖全部精确任务后，立即生成 `overview/ABCD_4x3.png` 并交付，不等待选择前正式视觉 QA。
- 首次达到 9/12 有效原图时只生成一次里程碑。
- 严格 4×3 的 12 张通过隔离视觉 Reviewer/Judge 总览验收后，集中复制原图、生成正式 `overview/ABCD_4x3.png`、校验输出，再写入 `status=completed`；审图通道不可用时不得伪造验收。
- 经典 Quick8 v5 在八张可用候选齐备后直接生成正式 `overview/ABCDEFGH_2x4.png`，把页面状态写为 `candidate_ready` 并等待用户选择；选择前不自动精修。Fast8 在八张齐备后必须先完成绑定当前完整候选集合的最终差异报告；若替代 1–2 席，替代结算后优先做 delta 碰撞组复核，必要时才全量复核一次。只有结果为 `pass|best_effort` 才能生成正式总览并写入 `candidate_ready`。
- 所有成功交付都必须先生成 `state/delivery_message.md` 并通过文本门，再逐字发送；Fast8 额外强制 `--fast8-links-only`，只允许两行总览与 A–H 九链接。禁止在校验后添加诊断文字或改成 `![...](...)`。
- 恢复时若原图已经齐全但状态仍为 `running`，优先生成总览和收口，禁止重新生图。
- `process_completed` 正式封存状态与 handoff 后，自动生成 `state/run_health_report.json|md` 并更新 `task_init.json` 指向的项目级集中监测索引。监测是只读、非视觉、尽力而为的派生动作；失败只返回 warning，不回滚完成态、不阻断交付、不增加图片或 Judge 调用。

## 后台运行监测

每次正式完成运行都按 `运行监测与批次复盘.md` 生成非视觉技术报告。报告复用现有状态、任务、事件、哈希、恢复和计时证据，不复制原始提示词或图片载荷；集中索引只保存轻量运行摘要、问题代码和报告路径。

默认集中根目录由 `init_task_dir.py` 写入 `state/task_init.json`。同一项目不同对话只要使用同一监测根目录，就会登记到相同 `entries/` 和 `index.json|md`。批次审查默认只读取 `index.json.pending_reviews`；`recent_10` 仅用于浏览和定位，不扫描旧聊天、JSONL 或全部图片。

自动监测不属于完成硬门，也不改变 `candidate_ready|accepted`、QA 范围或 30 分钟速度口径。需要补写历史完成运行时使用 `pipeline_control.py write-run-health`；需要重建索引时使用 `rebuild-monitoring-index`。

## 计时

记录：流程开始、用户决定收到、预检解决、任务文件创建、任务包完成、初始锚点同波派发、每张图片工具开始/结束、产物绑定或恢复、文件校验、运行时背压、技术错误、正式总览和流程完成。Fast8 另在 `diversity_review` 保存实际发生的自适应增量/最终 job、报告、候选集合哈希、替代预算和最终状态；差异替代仍通过正式派发事件记录。两种 8×1 初始图片若实际分波，只能由运行时背压造成并记录原因。

每个动作同时记录排队、Agent 回合、图片工具、文件回收和隔离 QA 时间，并通过 `pipeline_control.py` 当场写入。速度复盘以图片工具时间判断后端，以 Agent 回合时间判断长尾；Fast8 另报告八图完成到差异收口、替代图耗时和复核耗时，不把等待用户选择算入生成耗时。

Fast8 将“初始 A–H 派发至正式总览完成”设为 30 分钟软目标，并在 `timing_target` 中记录 `elapsed_minutes`、`met` 与 `soft_target_missed`。它不是图片与交付的硬截止：超过 30 分钟不得终止仍在运行的图片工具，不得跳过产物恢复、差异收口、文件校验、来源门禁或正式交接。Judge 例外地执行上述 180 秒无报告软超时；主控随后只向原会话请求一次不超过 45 秒的 report-only 写盘，不得用第二个完整视觉回合无限吞掉整体预算。

`run_health_report` 与集中索引在 `process_completed` 后生成，单独记录为监测开销，不并入正式 Fast8 的 `initial_anchor_dispatch -> formal_overview_completed` 软目标，也不得让索引存储故障改变正式计时结果。
